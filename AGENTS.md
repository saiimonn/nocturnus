## Architecture

Three top-level route groups split the app by audience. `app/(user)/*` (`browse`, `club/[slug]`, `events`, `events/[id]`, `faq`, `privacy`, `termsOfService`) is the **public, unauthenticated** consumer surface — no layout chrome, no auth guard (see Route protection below). `app/(owner)/*` (`dashboard`, `club/details`, `club/layout`, `owner-events`, `reservations`, `employees`) is the **authenticated venue-owner** surface, whose layout (`app/(owner)/layout.tsx`) wraps children in `SidebarProvider` + `AdminSidebar` (`components/Sidebar.tsx`) + `SidebarInset`. `app/(employee)/*` holds only `scan` (`/scan`, `/scan/[token]`) — the door-staff check-in flow. Its layout (`app/(employee)/layout.tsx`) is an async server component that itself verifies the session cookie and redirects non-employees to `/auth/login` (defence-in-depth alongside `proxy.ts`); it renders a minimal header (club name + the signed-in employee's name, via `EmployeeSignOut` in `app/(employee)/sign-out.tsx`) and no sidebar — a bouncer's phone has no use for owner navigation. `/` (`app/page.tsx`) redirects into the owner dashboard; `(user)` routes are reached directly (e.g. a shared `/club/[slug]` link), not via that redirect.

Navigation within the owner shell is data-driven, but not via the `navGroups`/`app-sidebar.tsx` names you might expect from older docs — **neither exists.** The real file is `components/Sidebar.tsx`, whose default export `AdminSidebar` renders five `NavigationType[]` arrays — `dashboardNavigation`, `customizationNavigation`, `bookingNavigation`, `eventsNavigation`, and `staffNavigation` (the last one holding the `/employees` link) — into three `SidebarGroup`s labeled "Overview," "Club Management," and "Staff." Adding an owner route means adding an entry to the relevant array, not editing JSX. Items render as plain links via their `href`; unlike what older docs claimed, there is currently no active/current-page highlighting logic (no `pathname.startsWith`, no `isActive` prop passed to `SidebarMenuButton`) — every nav item renders in the same visual state regardless of the current route.

Most owner pages and all `(user)` pages are live-wired to Supabase/the API layer (see below) — `lib/mock-data-owner.ts` and `lib/mock-data-user.ts` are mostly-superseded scaffold data that a few not-yet-wired owner screens (e.g. finance) still fall back to. The typed schema — the source of truth for every row shape — lives in **`lib/db.ts`** (the `Database` interface, 9 tables); new pages should fetch through the API layer / Supabase client and type against it rather than hardcoding arrays or reaching for the mock modules.

### Seeding the database

`npm run seed` (`scripts/seed.ts`, invoked via `tsx`) **wipes then repopulates** every Supabase table with constraint-valid faker data. It builds its **own** service-role Supabase client (distinct from the anon `lib/supabase.ts` singleton) to bypass RLS, so it needs `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env.local`; it fails fast if either is missing and prints the target host before wiping. Deletes run in FK-reverse order (`reservations → club_tables → club_images → floor_plans → events → club_employee_invites → clubs → users → owner_verification_tokens`) and inserts in FK-safe order — `users` (owners/admins) `→ clubs → users` (employees) `→ club_images/floor_plans/events → club_tables → reservations → owner_verification_tokens`. Employee rows insert in a **second** pass through `users`, after `clubs`, because `users.club_id` and `clubs.owner_id` form an FK cycle (a club needs an owner to exist first; an employee needs a club to exist first) — there is no ordering that satisfies both FKs in one pass. Adjust generated data shapes in `scripts/seed/factories.ts` and volume via the `COUNTS` object at the top of `scripts/seed.ts`. Verification-token plaintexts are printed to the console for out-of-band redemption. This is a **dev-only** tool — never point it at production.

**`COUNTS.floorPlansPerClub` must stay `1`** — `floor_plans.club_id` is `UNIQUE` (one floor plan per club; see Schema). It was previously `2`, which made the seed die on `floor_plans_club_id_key` partway through its insert sequence. Because `insertRows` calls `process.exit(1)` on the first error, a mid-sequence failure leaves the database **partially seeded and silently so**: `users`/`clubs`/`club_images` land, while `floor_plans`/`events`/`club_tables`/`reservations` — everything after the failing insert — stay empty. The visible symptom is every owner-dashboard stat reading `0` with the owner still able to log in, which reads like a query bug rather than a seed failure. If dashboard numbers are all zero, check the tail of the seed output for an `insert <table> failed:` line before suspecting the dashboard.

**Seeded reservations span past/today/future (~5:2:5) and their `status` is derived from that bucket**, not drawn independently: past bookings are `checked_in`/`cancelled`, today's are `confirmed`/`checked_in`/`pending`, future ones are `pending`/`confirmed`/`cancelled` — so nothing upcoming is ever already `checked_in`. Previously every `reservation_date` came from `faker.date.soon()` with an independently random status, which left the reservations **history** screen (it filters client-side to `cancelled`/`checked_in`) and the dashboard's "reservations today" permanently empty while generating rows that claimed to be checked in weeks before they happened. Keep date and status coupled when editing `makeReservation`.

Every seeded user shares one bcrypt-hashed password (`bcryptjs`, hashing the `SEED_PASSWORD` constant in `scripts/seed.ts`), so any of them can log in. Three fixed, memorable accounts lead the set and are forced `active`: **`owner@otus.dev`** (role `owner`, owns clubs), **`admin@otus.dev`** (role `admin`), and **`employee@otus.dev`** (role `club_employee`, `full_name` "Demo Door Staff," seeded as the first employee of the first club). Default password is `password123` — the seed run prints all three accounts and the password at the end.

### API layer

REST routes under `app/api/` follow a **thin-route** convention: each `route.ts` is a one-line re-export that maps HTTP verbs to named handlers, and all logic lives in `lib/api/<feature>/api.ts`. Example:

```ts
// app/api/clubs/route.ts
export { listClubs as GET, createClub as POST } from "@/lib/api/clubs/api"
```

Shared plumbing is in `lib/api/shared/`:
- `errors.ts` — the `ApiError` class + factories (`badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `notImplemented`, …), the `handle()` wrapper (catches thrown `ApiError`s and serializes them to JSON with the right status), `fromDb()` (unwraps a Supabase `{ data, error }`, throwing 500 on error / 404 on null), `readJson()`, `requireFields()`, and `RouteContext<T>` (whose `params` is a `Promise`, per Next 16). Handlers **throw** to signal failure — never hand-build error responses.
- `auth.ts` — the role guards (see Authentication below): `requireOwner()` reads/verifies the session cookie, throws `unauthorized` if there is none, and **itself asserts `session.role === "owner"`**, throwing `forbidden` otherwise, before returning `{ userId, role: "owner" }`. That assertion is load-bearing, not defensive boilerplate: `verifySession` now admits both owners and club employees (see Session below), so if `requireOwner()` didn't check the role itself, every owner-only endpoint — club/event/table CRUD, reservation management, the employee-invite endpoints — would be reachable by any authenticated employee. `requireClubOwner(clubId)` calls `requireOwner()` first, then additionally loads the club (service-role client) and throws `forbidden` unless `club.owner_id` matches. `requireEmployee()` is the employee counterpart: it throws `unauthorized` with no session, `forbidden` if `session.role !== "club_employee"`, then looks up the caller's `users` row (service-role client) to resolve `club_id` — throwing `forbidden` if the account is `suspended` or has no `club_id` — and returns `{ userId, role: "club_employee", clubId }`, letting callers scope every operation to that one venue without a second lookup. Every mutation guards on one of these three.
- `errors.ts` — the `ApiError` class + factories (`badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `tooManyRequests`, `notImplemented`, …), the `handle()` wrapper (catches thrown `ApiError`s and serializes them to JSON with the right status), `fromDb()` (unwraps a Supabase `{ data, error }`, throwing 500 on error / 404 on null), `readJson()`, `requireFields()`, and `RouteContext<T>` (whose `params` is a `Promise`, per Next 16). Handlers **throw** to signal failure — never hand-build error responses. `ApiError` also carries an optional `headers` bag that `handle()` spreads onto the response; it exists so `tooManyRequests(retryAfterSeconds)` can emit `Retry-After`, and is `undefined` on every other error, which serialize exactly as before.
- `rate-limit.ts` — `enforceRateLimit(request, scope, limit, windowSeconds)`, the per-IP fixed-window limiter for unauthenticated endpoints (see Authentication below).
- `auth.ts` — the owner guards, now **implemented** (see Authentication below): `requireOwner()` reads/verifies the session cookie and returns `{ userId, role: "owner" }` or throws `unauthorized`; `requireClubOwner(clubId)` additionally loads the club (service-role client) and throws `forbidden` unless `club.owner_id` matches. Every mutation guards on one of these.

### Authentication

Auth is **custom credentials**, not Supabase Auth: `users.password_hash` is a bcrypt hash (`bcryptjs`, now a runtime dependency). **`role === "owner"` or `role === "club_employee"` can log in** — `admin` and suspended accounts are rejected. Rejection is deliberately undifferentiated: a missing user, a wrong password, and an `admin` account all produce the same generic 401, so the response never discloses which one failed.

- **Session:** a signed JWT (`jose`, HS256, 7-day expiry) in an `HttpOnly` cookie named `otus_session`, keyed by `AUTH_SECRET` (required env var, in `.env.local`). The cookie contract lives in **`lib/api/auth/session.ts`**, whose exported `Session` type is now `{ userId: string, role: "owner" | "club_employee" }` (`SessionRole`) — the old `OwnerSession` type no longer exists. `createSession`/`verifySession` admit either role; `verifySession` no longer implies "this caller is an owner" by itself — anything that must restrict access to one role (`requireOwner()`, `requireEmployee()`, `getOwnerProfile()`) asserts `session.role` explicitly (see `auth.ts` guards above). `SESSION_COOKIE`/`sessionCookieOptions` are unchanged. Nothing outside this module touches JWTs directly.
- **Endpoints** (`lib/api/auth/api.ts`, thin routes under `app/api/auth/`): `POST /api/auth/login` (`readJson` → verify email+password → set cookie → return the safe user fields, never `password_hash`; generic 401 for missing user / bad password / a non-loginable role (`admin`), 403 for suspended) and `POST /api/auth/logout` (clears the cookie). `redeemVerificationToken` (`POST /api/auth/verification/redeem`) is implemented: validates the token (sha256 hash lookup against `owner_verification_tokens`, rejecting used/revoked/expired), enforces email uniqueness and an 8-character password minimum, atomically claims the token (`UPDATE ... WHERE used = false` before inserting the user, so a losing race never creates a duplicate account), creates the `owner` user (bcrypt-hashed password), and sets the session cookie exactly like `login`. A companion read-only `checkVerificationToken` (`POST /api/auth/verification/check`) lets the register UI validate the token in step 1, before the user fills in account details, without consuming it.
- **Register UI (`app/auth/register/page.tsx`):** a single client component, now fully wired — step 1 calls `checkVerificationToken`, step 2 calls `redeemVerificationToken` (which sets the session cookie), and step 3 calls the existing `createClub` (`POST /api/clubs`), then redirects to `/dashboard`. Three steps, `useState<1 | 2 | 3>`: **1** token verification (`inviteToken`); **2** user details (`fullName`, `email`, `contactNumber` optional, `password` + `confirmPassword` with a client-side match check before advancing) — `fullName` is required here because `redeemVerificationToken` requires it; **3** club registration (`clubName`, `address`, `description` optional) — fields mirror `createClub`'s `name`/`address`/`description`, no `venueType`/city-breakdown fields since `Clubs` has no matching columns. Back navigation steps back one at a time and preserves state; visual style is the bespoke dark palette (`#0a0a0a`/`#141414`), intentionally not shadcn/ui, matching `app/auth/login/page.tsx`.
- **Employee invite/onboarding is fully implemented**, via a table deliberately separate from the owner's `owner_verification_tokens`: `club_employee_invites` (migration `0002_club_employees.sql`) carries `club_id` and `email` alongside its `token_hash`/`expires_at`/`used`/`revoked` columns. This is the opposite design from the owner token, which is deliberately club-less (see workflow 2 in Domain Context) — an employee invite *asserts venue identity* (this person, this club) up front, because the owner who issues it already knows both, whereas an owner-account token cannot know a club that doesn't exist yet. A partial unique index (`club_employee_invites_one_live_per_email`, scoped to `used = false and revoked = false`) allows at most one live invite per club+email at a time. `users.club_id` (nullable FK to `clubs`, `on delete cascade`) is what an employee account resolves through `requireEmployee()`; a check constraint (`users_club_id_role_check`) enforces `(role = 'club_employee' and club_id is not null) or (role <> 'club_employee' and club_id is null)`, i.e. every employee must have a club and every owner/admin must not — both directions enforced at the database level, not just by convention.
  - **Owner-side management** (`lib/api/employees/api.ts`, all guarded by `requireOwnClub()` → `requireOwner()` internally, so an owner only ever sees their own club's staff/invites): `listEmployees` (`GET /api/owner/employees`) returns that club's `club_employee` users plus its live (unused, unrevoked) invites; `inviteEmployee` (`POST /api/owner/employees/invite`) validates the email, rejects it if an account or a live invite already exists for that address, inserts the invite row, and emails a registration link (`${NEXT_PUBLIC_APP_URL}/auth/employee/register?token=<plaintext>`); `revokeInvite` (`DELETE /api/owner/employees/invites/[inviteId]`) sets `revoked = true`, scoped by `club_id`; `updateEmployee` (`PATCH /api/owner/employees/[employeeId]`) toggles an employee's `status` between `active`/`suspended`, scoped by `club_id` **and** `role = 'club_employee'` so an owner can never touch another club's staff or their own user row through this endpoint.
  - **Invite email sends are not best-effort — this is a deliberate contrast with the reservation-confirmation email**, which is wrapped in try/catch and swallows failures because a missed confirmation email is recoverable (the owner can re-trigger it, or the guest can look up their reservation another way). An invite email is not: the plaintext token exists only in that one email, is never stored, and cannot be regenerated or resent from the invite row — so if the send silently failed, the invite row would sit in the table looking exactly like a delivered one, with no way to know or recover. `inviteEmployee` therefore inserts the invite row first (the token must be persisted before it can be emailed), attempts the send, and if `sendEmail` throws, deletes the invite row it just inserted and rethrows — so the owner sees a failure and can retry, rather than a phantom pending invite. (If `RESEND_API_KEY` is simply unset, `sendEmail` returns `false` rather than throwing, and the invite row is kept with the link logged to the console — see `sendEmail` below.)
  - **Redemption** mirrors the owner token flow but scoped to `club_employee_invites`. `checkEmployeeInvite` (`POST /api/auth/employee-invite/check`, `lib/api/auth/api.ts`) is a read-only sha256 hash lookup that rejects a used/revoked/expired invite and returns `{ valid: true, email, clubName }` (joining `clubs(name)`) so the registration UI can preview the invite before the user commits. `redeemEmployeeInvite` (`POST /api/auth/employee-invite/redeem`) takes only `{ token, full_name, password, contact_number? }` — **the account email always comes from the invite row, never the request body**, so a forwarded invite link is useless to anyone but the invited address. It enforces email uniqueness, then atomically claims the invite (`UPDATE ... WHERE used = false` before the insert, same race-proof ordering as `redeemVerificationToken`) before creating the `club_employee` user with `club_id` copied from the invite and `status: "active"`, and sets the session cookie via `createSession({ role: "club_employee" })`. `app/auth/employee/register/page.tsx` (client component) is the single-step counterpart to the owner's three-step register page: it reads `?token=` via `useSearchParams` (wrapped in `Suspense`, required by the App Router), calls `checkEmployeeInvite` on mount to show a read-only prefilled email and the club name, then submits name/password/optional contact number to `redeemEmployeeInvite` and redirects to `/scan` on success — same bespoke dark palette as the owner auth pages.
  - The owner-facing UI is `app/(owner)/employees/page.tsx` (client component), reachable via the sidebar's "Staff" group (`staffNavigation` in `components/Sidebar.tsx`): it fetches `GET /api/owner/employees` on mount, lists current employees and pending invites, and its invite form / revoke / suspend-toggle actions call the endpoints above.
- **Rate limiting:** all three unauthenticated auth endpoints call `enforceRateLimit` (`lib/api/shared/rate-limit.ts`) as their **first** statement, before `readJson` and before any bcrypt work, so blocked requests cost nothing beyond the counter write. Limits are per-IP, per-endpoint, fixed-window: `login` 15/15min, `verification/check` 10/15min (tightest — it reports token validity *without consuming the token*, making it a brute-force oracle), `verification/redeem` 5/hour. `logout` is unlimited (authenticated, idempotent). Counters live in the `rate_limits` table and are incremented by the `bump_rate_limit(p_key, p_window_seconds)` Postgres function — a single statement, because a read-then-write from app code races under exactly the concurrency an attacker generates. **In-memory counters are not an option here:** this deploys to Vercel, where instances are ephemeral and concurrent, and Fluid Compute reuses them often enough that a `Map` would pass manual testing and fail under load. The limiter **fails open** — an RPC error logs and allows the request, since login already requires Supabase to be reachable, so failing closed would convert a DB blip into a total auth outage. IP resolution prefers `x-real-ip` (Vercel sets it) over the first entry of `x-forwarded-for`; the Next dev server supplies these locally too, resolving to the IPv6 loopback (keys log as `auth:login:::1`), so **you will trip your own limits while testing locally** — every local client shares the one loopback address. A `local-unknown` bucket exists as a defensive fallback for runtimes that supply neither header. The RPC is typed locally in `rate-limit.ts` via a narrow cast because `lib/db.ts` declares `Functions: Record<string, never>` — fold it into the generated types on the next regeneration.
- **Reads use the service-role client** (`lib/supabase-admin.ts`, `supabaseAdmin`) because RLS hides the `users` table from the anon key and `password_hash` must never be exposed through it. Import it **server-side only**.
- **Route protection:** `proxy.ts` at the repo root (Next 16 renamed `middleware` → `proxy`; it defaults to the Node.js runtime) is now **role-aware**, not just an anonymous/authenticated gate. It verifies the cookie and redirects anonymous users to `/auth/login`; if the session is valid it checks the pathname against an `OWNER_PREFIXES` list (`/dashboard`, `/reservations`, `/owner-events`, `/club/details`, `/club/layout`, `/employees`) and redirects a non-owner hitting one of those to `/scan`, and separately redirects a non-employee hitting `/scan` to `/dashboard` — so a signed-in user in the wrong group is bounced to their own home rather than shown a 403, since each role has exactly one place it belongs. Its `matcher` covers `/dashboard/:path*`, `/reservations/:path*`, `/owner-events/:path*`, `/club/details/:path*`, `/club/layout/:path*`, `/employees/:path*`, and `/scan/:path*` (NOT `/club/[slug]`, which is a public `(user)` page).
- **Login UI:** `app/auth/login/page.tsx` POSTs to `/api/auth/login` and routes by the returned role — `router.push("/scan")` for `club_employee`, `router.push("/dashboard")` for everyone else (i.e. `owner`).
- **Logout UI:** the "Sign out" item in the owner sidebar's footer dropdown (`components/Sidebar.tsx`) POSTs to `/api/auth/logout`, then `router.push("/auth/login")` + `router.refresh()`.
- **Session in the UI:** `getOwnerProfile()` (`lib/api/shared/auth.ts`) resolves the cookie to the owner's `{ id, full_name, email }` and returns `null` rather than throwing, so **server components** can use it (`requireOwner()` throws an `ApiError`, which only `handle()` knows how to serialize — it is for route handlers only). `app/(owner)/layout.tsx` is an async server component that calls it, redirects to `/auth/login` if the user row is gone, and passes a `SidebarUser` prop down to the client `AdminSidebar`. This is the pattern for surfacing session data in the owner shell — don't re-fetch it client-side.

Handler modules: `clubs`, `reservations`, `users`, `onboarding` (verification tokens), `finance`, `auth`, `events`. **Cross-tenant reads are implemented** against Supabase; selects deliberately omit `password_hash` (users) and `token_hash` (tokens). **Owner login/logout are implemented** (see Authentication above). **Owner event fetching is implemented:** `GET /api/owner/events` → `listOwnerEvents` (`lib/api/events/api.ts`) guards with `requireOwner()`, resolves the caller's single club via `clubs.owner_id` with `.maybeSingle()` (an owner owns exactly one club — enforced by a `UNIQUE` constraint on `clubs.owner_id`, so this cannot match multiple rows), and returns `{ clubId, events }` — that club's events in **all** statuses (draft/published/cancelled) using the **service-role** client so drafts hidden from consumer surfaces stay visible to their owner. **Event CRUD is fully implemented** in `lib/api/events/api.ts`: `createEvent` (`POST /api/owner/clubs/[clubId]/events`), `updateEvent` (`PATCH .../events/[eventId]`), and `deleteEvent` (`DELETE .../events/[eventId]`) all guard with `requireClubOwner(clubId)` and write via the service-role client; update/delete additionally scope by `club_id` so an owner can only touch events on their own club, and both 404 on a non-matching row. `status` is validated against `draft|published|cancelled`. The owner events page (`app/(owner)/owner-events/page.tsx`, a client component) fetches `/api/owner/events` on mount and its Add/Edit/Delete call the mutation endpoints, submitting as `multipart/form-data` (an optional `image` file plus the text fields) so `createEvent`/`updateEvent` can upload the banner — see the shared Storage helper described below. **Owner→club creation is implemented:** `createClub` (`POST /api/clubs`, `lib/api/clubs/api.ts`) guards with `requireOwner()`, then checks (service-role client) whether the caller already owns a club and throws `conflict` if so — this is what gives `Clubs.owner_id` its `UNIQUE` invariant an application-level guard, on top of the matching DB constraint (see below). It requires `name`/`address` in the JSON body, slugifies `name` into a unique `slug` (retrying with a random suffix on collision), and inserts the row as `status: "draft"`. the live DDL declares `clubs.owner_id uuid NOT NULL UNIQUE` to match what `DB.md`/this file always documented — previously the `UNIQUE` constraint was only in the docs, not the live DDL. (That DDL is **not** `supabase/schema.sql` — despite older references to that path, it is gitignored/untracked, dumped locally for reference only; `.gitignore` excludes all of `supabase/*` except `!supabase/migrations/`, so `supabase/migrations/*.sql` is this repo's only tracked, reviewable source of schema history — see Schema below.) **Club CRUD (details, images, floor plans, tables) is now fully implemented** in `lib/api/clubs/api.ts`: `getOwnerClub` (`GET /api/owner/club`) resolves the caller's own club from the session the same way `listOwnerEvents` does (`.eq("owner_id", userId).maybeSingle()`), returning `{ club: null }` if they haven't registered one yet; `updateClub` (`PATCH /api/owner/clubs/[clubId]`) patches name/address/description/cover_image_url/operating_hours and restricts `status` to `draft`/`active` only (`inactive` stays superadmin-only, per the lifecycle rule above); `addClubImage`/`deleteClubImage`, `createFloorPlan`/`updateFloorPlan`/`deleteFloorPlan`, and `createTable`/`updateTable`/`deleteTable` all guard with `requireClubOwner(clubId)` and scope mutations by `club_id` (and `floor_plan_id` for tables), 404ing on a non-matching row, matching the `events` CRUD pattern. **Owner reservation management is now implemented** in `lib/api/reservations/api.ts`: `listClubReservations` (`GET /api/owner/clubs/[clubId]/reservations`) guards with `requireClubOwner(clubId)` and returns `{ clubId, reservations, tables }` — every reservation for that club across **all** statuses (pending/confirmed/cancelled/checked_in), newest `reservation_date` first, plus that club's tables across every floor plan (so the owner UI can resolve `table_id` → label without a per-floor-plan round trip), all via the service-role client. `updateReservation` (`PATCH /api/reservations/[id]`) only carries the reservation id in the route, so it first reads the existing row (service-role client) to learn its `club_id`, then delegates to `requireClubOwner(that club_id)` — this is the authorization check, and it 404s before the ownership check if the reservation doesn't exist. It accepts a partial JSON body (`status`, `party_size`, `reservation_date`, `table_id`); `status` is validated against `pending|confirmed|cancelled|checked_in` the same way `events.status` is validated, `party_size` must be a positive integer, any omitted field is left untouched, and transitioning `status` to `confirmed` auto-generates a `qr_code_token` (via `crypto.randomUUID()`) if the row doesn't already have one — `checkinReservation` looks reservations up by that token, so confirming is what makes a booking checkinable at the door. When a PATCH transitions a reservation from a non-confirmed status into `confirmed`, `updateReservation` additionally makes a **best-effort** call to `sendReservationConfirmation` (`lib/api/reservations/confirmation.ts`): it generates a QR PNG via `generateQrPng` (`lib/qr.ts`, `qrcode`) — which encodes not the bare `qr_code_token` but the full check-in URL `${NEXT_PUBLIC_APP_URL}/scan/{token}`, because a phone's native camera app only offers a tap-through when the payload is a URL — uploads the PNG to the `club-media` bucket under `reservations/{reservationId}/` via the `uploadClubMediaBytes` helper, renders the `emails/reservation-confirmed.tsx` React Email template, and sends it to `guest_email` via Resend (`lib/email/client.ts`). Encoding a URL instead of a raw token is only safe because `/scan/[token]` requires a `club_employee` session (see Route protection above) — the QR lands in the guest's own inbox, so an unguarded link would let guests check themselves in from home; that guard is what makes the URL-payload choice safe, and it must not be weakened. The send is guarded to fire only on the actual transition (re-confirming an already-`confirmed` row sends nothing) and is wrapped in try/catch so an email failure logs but never fails the confirm — the codebase's one deliberately best-effort email send, in contrast to the employee invite send documented above. `sendEmail` (`lib/email/client.ts`, renamed from `sendReservationEmail` now that it is shared by both the reservation-confirmation and employee-invite flows) returns `boolean`: `true` if Resend actually sent, `false` if `RESEND_API_KEY` is unset (a no-op with a console warning), letting callers choose best-effort (ignore the return) or strict (check it, as `inviteEmployee` does). This is the codebase's only outbound-email integration; it needs `RESEND_API_KEY`, `EMAIL_FROM`, and `NEXT_PUBLIC_APP_URL` in `.env.local` (the `onboarding@resend.dev` sandbox sender only delivers to the Resend account owner until a domain is verified; `NEXT_PUBLIC_APP_URL` is also what `generateQrPng` and `inviteEmployee`'s registration links are built from). **`NEXT_PUBLIC_APP_URL` is required, not optional** — `lib/qr.ts` throws when it's unset, and because `updateReservation` wraps the whole confirmation send in a swallowed try/catch (see above), a missing value doesn't fail the confirm request; it silently sends the guest nothing, with only a `console.error` naming the cause as evidence. And because it's a `NEXT_PUBLIC_*` value, Next.js inlines it into the client/server bundles at **build** time — setting it only in the runtime environment after `npm run build` has already run does not work; it must be present when the app is built, and the app rebuilt/redeployed after it changes. The door scanner UI is implemented — see `checkinReservation` and the employee flow above — and the auto-cancel of un-checked-in confirmed reservations is still not built. `checkinReservation` (`POST /api/reservations/checkin`, `lib/api/reservations/api.ts`) now requires `requireEmployee()` (previously token-only, no session auth) and looks the reservation up via the service-role client; a token belonging to another club is rejected as `notFound` ("No reservation matches that code"), **not** `forbidden`, so the response never discloses that the code is valid at a different venue. The owner reservations UI (`app/(owner)/reservations/requests/page.tsx` and `.../reservations/history/page.tsx`, both client components) resolves the caller's `clubId` via `GET /api/owner/club` first, then fetches `/api/owner/clubs/{clubId}/reservations` and `/api/owner/events` (for event-title display) in parallel; **requests** shows pending/confirmed/cancelled and its Confirm/Decline actions `PATCH /api/reservations/{id}` with `{ status: "confirmed" | "cancelled" }`, while **history** is read-only and filters client-side to cancelled/checked_in. **The owner dashboard is now live-wired too:** `app/(owner)/dashboard/page.tsx` (a client component) follows the same `GET /api/owner/club` → `{clubId}/reservations` + `/api/owner/events` fetch sequence as the reservations pages, deriving its stat cards, "tonight's overview," recent-reservations list, and upcoming-events list from the fetched `reservations`/`clubTables`/`events` instead of `mock-data-owner.ts`; it renders loading/error/no-club-yet states before the real layout.

**Every club-owned image is now a real file upload, not a pasted URL — this is the codebase's only Storage integration.** `lib/api/shared/storage.ts` holds the shared helpers: `requireImageFile`/`optionalImageFile` pull a `File` off a `FormData` field (validating `image/*` MIME type, capped at 8MB) and `uploadClubMedia(pathPrefix, file)` uploads it (service-role client) to the public `club-media` Supabase Storage bucket under `${pathPrefix}/${crypto.randomUUID()}.<ext>` and returns the bucket's public URL — the bucket (public read, 8MB limit, image MIME allowlist) was created via a migration (`create_club_media_storage_bucket`) alongside a `storage.objects` public-select policy scoped to `bucket_id = 'club-media'`; all writes go through the service-role client so no write policy is needed. Every endpoint that persists an `image_url`/`cover_image_url` column now reads `multipart/form-data` instead of JSON and calls these helpers: `addClubImage` (`file` field → `clubs/{clubId}/gallery`), `updateClub`'s optional `cover_image` field (→ `clubs/{clubId}/cover` — `updateClub` still accepts a plain JSON body for status-only/text-only PATCHes such as the publish/draft toggle, switching on the request's `Content-Type` header), `createFloorPlan`/`updateFloorPlan`'s `image` field (→ `clubs/{clubId}/floor-plans`), and `createEvent`/`updateEvent`'s optional `image` field (→ `clubs/{clubId}/events`). A `PATCH` that omits a file field leaves the existing image untouched (checked via `form.has`, since `FormData.get` can't distinguish "omitted" from "explicitly empty" the way a JSON body's `undefined`/`null` can). `uploadClubMediaBytes(pathPrefix, bytes, contentType, extension)` is the bytes-based sibling of `uploadClubMedia` for server-generated media (the reservation QR PNG); `uploadClubMedia` now delegates to it.

The owner club-details screen (`app/(owner)/club/details/page.tsx`, a client component) now fetches `/api/owner/club` on mount plus the club's images via the existing public `GET /api/clubs/[slug]/images` (images/floor-plans/tables are RLS-readable regardless of club status, so this works for a `draft` club too). It renders a cover-image banner (falling back to "No cover image") with an upload control while editing, and its Edit/Save (now including the club **name**, not just description/address) submits as `multipart/form-data` whenever a new cover image was picked (plain JSON otherwise) — plus photo add/remove call the mutation endpoints, with the photo-add control now a file `<input type="file">` uploading via `FormData` — no more `mock-data-owner.ts` on this page. Outside edit mode, a status-toggle button (hidden only when `status === "inactive"`, the superadmin-only state) calls `updateClub` with `{ status: "active" }` or `{ status: "draft" }` — labeled "Publish club" while draft, "Move to draft" while active — letting the owner move their club live or pull it back to draft. **The floor-plan layout editor (`app/(owner)/club/layout/`, built on `react-konva`) is now wired to these endpoints.** `floorplanCanvas.tsx` (a client component) fetches the caller's club via `/api/owner/club`, then that club's floor plans via the public `GET /api/clubs/[slug]/floor-plans` (works pre-publish, same RLS-readable-regardless-of-status reasoning as club images) and takes the first one as the single editable floor plan; its tables load via `GET /api/clubs/[slug]/floor-plans/[floorPlanId]/tables`. The floorplan background is now set by uploading a file (an object-URL preview renders in the canvas immediately, ahead of the actual upload) rather than pasting an image URL — that upload persists via `createFloorPlan`/`updateFloorPlan` (`POST`/`PATCH /api/owner/clubs/[clubId]/floor-plans[/[floorPlanId]]`) the first time a floor plan doesn't yet exist vs. after. Table add/edit/delete and drag-to-reposition/resize all call `createTable`/`updateTable`/`deleteTable` (`.../floor-plans/[floorPlanId]/tables[/[tableId]]`) — position changes persist `pos_x`/`pos_y` on drag end. No more `mock-data-owner.ts` on this page. Finance is fully stubbed because no payments/PayMongo table exists in `DB.md` yet (the numbers live only as `mock-data.ts` aggregates). Note the DB-typed client narrows enum columns to string-literal unions, so `.eq("status", value)` on a filter needs a cast to that union.

## Domain Context

This repo is **both** the consumer (guest/end-user) app and the venue-owner portal for Otus — a Cebu nightclub reservation platform — in one Next.js app (see Architecture above for the `(user)`/`(owner)` split). It is a **separate repository** only from the superadmin (God-Mode) portal — token issuance, the global reservation ledger, and financial reconciliation live over there, not here — but both repos read and write the **same Supabase database**. Expect to need `SUPABASE_SERVICE_ROLE_KEY` to bypass RLS for cross-tenant/service-role reads.

Four workflows define what this repo is for:

1. **Guest browsing and booking (`(user)`, public, no account).** Anyone can browse published clubs (`/browse`, `GET /api/clubs`, `.eq("status", "active")` only), view a club's detail page and events, and book a table as a guest — `POST /api/reservations` has no auth guard and writes guest identity (`guest_name`/`guest_email`/`guest_contact`) directly onto the reservation row, since guests have no accounts (`Users.role` is `owner`/`admin`/`club_employee` only). Guests can also look up their own reservation via `GET /api/reservations/[id]` with an `X-Guest-Email` header. Checking in is now the door staff's job, not the guest's — see workflow 4. None of this requires the onboarding/auth flow below — that's owner-only.

2. **B2B white-glove onboarding (owner-only).** Venue owners cannot self-serve signup — an account exists only by redeeming a token a superadmin issued (elsewhere). The order is **owner first, club second**, and both steps after the first happen *in this repo*:

   1. A superadmin generates a secure one-time token in the superadmin portal. It is **not tied to any club** — it carries only an expiry.
   2. The token is handed to the venue manager out-of-band and redeemed **here** (`redeemVerificationToken`) to create their authenticated `owner` account. Redemption creates the user and marks the token `used`; it links no club, because none exists yet.
   3. The now-authenticated owner registers their **own** club **here**, as `draft`. This is how `Clubs.owner_id` gets its value.

   **A token gates account creation, not venue identity.** It proves the holder is an approved owner; it does not prove they own any particular venue. Nothing structurally stops a token holder from registering a club under a name that isn't theirs and publishing it — the backstop is reactive: a superadmin spots it and flips the club to `inactive`. That trade is accepted deliberately; do not write code or docs that assume the token already guarantees venue identity.

   **Why the token has no `club_id`:** `Clubs.owner_id` is `FK, NO NULL`, so a club cannot exist before its owner does. Owner-first is what makes that constraint satisfiable, and it is why `DB.md` states no owner association is stored on the token. Club creation lives in this repo, never in the superadmin portal.

   **Clubs status lifecycle:** `draft` → `active` → `inactive`. A club is created by its **owner** as `draft` and is **hidden from all consumer surfaces** — `listClubs`/`getClub` in `lib/api/clubs/api.ts` filter `.eq("status", "active")`, so `draft` and `inactive` never surface. The owner fills in images, description, and hours, then publishes (`draft` → `active`) via `updateClub` (`requireClubOwner`) — *when* a venue is showcased is up to the owner, not the superadmin. `inactive` is a superadmin-only enforcement state (fraud offline); owners cannot set it.

   **Employee onboarding is the opposite shape of this, deliberately.** Where an owner token gates *account creation* but proves nothing about venue identity, a `club_employee_invites` row gates account creation **and** asserts venue identity in the same step — it is issued by an already-verified owner who names both the invitee's email and their own `club_id`. There is no equivalent "register a club afterward" step for employees: redemption produces a fully club-bound account immediately. See "Working the door" below and the Authentication section's employee-flow subsection for the mechanics.

3. **Running the club day-to-day (owner-only).** Once registered, the owner manages their own club's details/images/floor plans/tables, creates and edits events, and works reservations for that club (confirm/decline/check-in), and manages their door staff (invite/revoke/suspend — see workflow 4). Guest identity is denormalized onto the reservation row (`guest_name`, `guest_email`, `guest_contact`) specifically so bookings work for walk-ins and guests without accounts — do not assume a reservation joins to a user. Everything here is scoped to `requireClubOwner`/the caller's own `club_id`; there is no cross-club view in this repo — that (plus financial reconciliation of PayMongo volume/commission/payouts) is the superadmin portal's job.

4. **Working the door (employee-only).** A `club_employee` account exists only via owner invite (workflow 2's note above) and can do exactly one thing: sign in and check guests in at `/scan`. `requireEmployee()` resolves the session to that employee's single `club_id`; `checkinReservation` (`POST /api/reservations/checkin`) uses it to scope every lookup, so an employee can only check in reservations belonging to their own club — a token from another club 404s as "no reservation matches," never revealing that it is valid elsewhere. There is no cross-club, cross-role, or admin capability on this surface; `proxy.ts` enforces that an employee session never reaches an owner route and vice versa (see Route protection in Authentication above).

### Schema

`DB.md` is the schema reference. Note two conventions that will bite you: primary keys are UUID v4, and `club_id` is **intentionally denormalized** onto both `Club_Tables` and `Reservations` to avoid joins on hot queries. All timestamps are UTC; convert at the application layer. There is no tracked `supabase/schema.sql` in this repo — `.gitignore` excludes `supabase/*` except `!supabase/migrations/`, so `supabase/migrations/*.sql` (applied in filename order, e.g. `0002_club_employees.sql`) is the only versioned, reviewable record of DDL history. Don't assume a full schema dump exists on disk or in git; if you need the live shape of a table, read the relevant migration(s) or query the database.

✅ **Naming conflict resolved.** `DB.md` is the source of truth. Tables are `Clubs`, `Users`, `Owner_Verification_Tokens`, `Club_Employee_Invites` (PascalCase). `Users.role` accepts `owner`, `admin`, or `club_employee`; `Users.club_id` is a nullable FK to `Clubs`, required (by a CHECK constraint) exactly when `role = 'club_employee'` and forbidden otherwise — guests still have no accounts.
